# CLAUDE.md

Guidance for Claude Code (and other agents) working in this repository.

## What this is

Coco Instruments — a Telegram Mini App (React + Vite + TypeScript, Zustand store,
HashRouter) with a small Node/Express backend (`server.js`). Sections: finance,
notes (+ graph), people, clothing/wardrobe, a gesture-driven calculator, and a games
hall (Slots, Cascade and the top-down mining game «Каторга», all on one shared wallet).

## Commands

- `npm run dev` — Vite dev server.
- `npm run build` — typecheck (`tsc --noEmit`) + production build. Run before pushing.
- `npm test` — Vitest unit tests (`src/lib/*.test.ts`).
- `npm start` — run the Express server (serves `dist/` + `/api`).

## Deployment & branches — READ THIS BEFORE PUSHING

Production is a VPS, deployed **automatically by GitHub Actions**.

- **The `prod` branch is production for this React app.** `.github/workflows/deploy.yml`
  triggers on every push to `prod`: it SSHes into the VPS, runs `deploy/setup.sh` (which
  resets the server's checkout to `origin/prod`, rebuilds, and restarts the `coco`
  service), then repoints the Telegram bot's menu button. **Nothing deploys from any
  other branch.**
- **⚠️ `main` is NOT this app.** The `main` branch holds an old, unrelated version of
  Coco (vanilla HTML/JS — `coco-money.html`, `debts.html`, `scale-calculator.html`, …)
  with a separate history. Do not deploy from it, merge into it, or overwrite it.
- **To ship a change, get it onto `prod`.** Each web session is given its own working
  branch (e.g. `claude/<name>`). That branch does **not** auto-deploy. When the work is
  approved, fast-forward / merge it into `prod` and push `prod` — the Action does the
  rest.
- **Ship without asking.** The owner has no other way to try a change than on the live
  bot, so every finished piece of work goes straight to `prod`: build, test, bump the
  version, commit to the session branch, fast-forward `prod`, push. Do **not** stop to
  ask for confirmation — that is a standing instruction from the owner.
- Required GitHub Actions secrets (already configured): `VPS_HOST`, `VPS_PASSWORD`,
  `BOT_TOKEN` (optional: `VPS_USER`, `DOMAIN`, `GH_TOKEN`, `ADMIN_CHAT_ID`). Without
  them the workflow stays green and simply skips.
- **Data lives in `/var/lib/coco`** (`store/` = per-user app data, `uploads/` = photos,
  `reminders.json`, `admin.json`) — outside the app checkout, so deploys never touch it.
  A daily systemd timer (`coco-backup.timer`) archives it, keeps the last 14 copies in
  `/var/lib/coco/backups`, and sends the archive to the admin via the bot. Bot commands:
  `/backup` (send a copy now), `/id` (get your chat id). Restore on a new box:
  `sudo bash deploy/restore.sh <archive>.tar.gz`.
- The branch name is referenced in several places — keep them in sync if it is ever
  renamed: `.github/workflows/deploy.yml` (trigger + `BRANCH`), `deploy/setup.sh`,
  `deploy/redeploy.sh`, `deploy/README.md`, and `server.js` (`GH_REF`).
- Manual redeploy on the box: `sudo bash /opt/coco/deploy/redeploy.sh`. Manual run from
  GitHub: Actions → "Deploy to VPS" → "Run workflow" (`workflow_dispatch`).

> По-русски: прод живёт на VPS и выкатывается сам при пуше в ветку **`prod`** (GitHub
> Action «Deploy to VPS» — собирает на сервере и перенацеливает кнопку бота). Ветка
> **`main` — это СТАРОЕ приложение** (Coco на чистом HTML/JS), её не трогаем. Любая
> рабочая ветка сессии в прод НЕ едет — чтобы задеплоить, изменения нужно влить в
> `prod` и запушить её. **Подтверждения спрашивать не надо** — владелец проверяет
> только в проде, поэтому готовую работу сразу катим туда.

## Сеть: домен, Cloudflare и Telegram — НЕ ТРОГАТЬ НАУГАД

Сервер стоит на российском IP (`31.184.198.91`, handy.host). Telegram в России
заблокирован, и из этого следует всё остальное:

- **Домен `coco-instruments.ru` должен быть ЗА прокси Cloudflare (оранжевое
  облачко).** Обе записи `A` — апекс и `www` — в режиме Proxied, SSL/TLS = Full.
  Проверено 19.09.2026: с серым облачком у пользователей с заграничным VPN
  вместо приложения был белый экран (соединение устанавливается, тело ответа
  не приходит), с оранжевым — всё грузится.
- **Почему так, хотя раньше было наоборот.** В коде долго жил шаг, который
  принудительно переводил домен в серый режим: прокси Cloudflare в России
  режет ответы примерно на 16 КБ, и для тех, кто ходит из России напрямую,
  серый режим действительно лучше. Но Telegram в России закрыт — значит **все**
  пользователи мини-приложения приходят через VPN с заграничными выходами, а
  для них верно ровно обратное. Старое рассуждение осталось в комментариях и
  легко уводит не туда: не верьте им, верьте этому абзацу.
- Деплой режим прокси больше не меняет, только докладывает. Переключить
  вручную — workflow «DNS check (Cloudflare grey cloud)».
- **Вебхук запоминает IP, а не имя.** Telegram резолвит домен один раз, при
  регистрации, и сам DNS не перечитывает; `setWebhook` с тем же адресом
  отвечает «Webhook is already set» и ничего не меняет. После переключения
  домена на Cloudflare он из-за этого продолжал ходить на старый IP и получать
  «Connection timed out». Лечится `deleteWebhook` + `setWebhook` с явным
  параметром `ip_address` — деплой теперь вычисляет адрес из живого DNS на
  каждом прогоне и передаёт его. Признак беды: в `getWebhookInfo` поле
  `ip_address` затёрто маской секретов (значит совпадает с `VPS_HOST`, то есть
  указывает мимо Cloudflare). Когда всё верно, там видны настоящие цифры
  адреса Cloudflare. Проверено 19.09.2026 — после этого вход на сайте ожил.
- **Сервер не ходит НАРУЖУ к `api.telegram.org`** — и, видимо, не будет, пока
  стоит в России. Это не чинится оранжевым облачком (оно только про входящие),
  зато обходится: всё, что сервер отправляет сам, доставляют раннеры GitHub.
  Они достают и VPS, и Telegram. `reminders.yml` шлёт напоминания,
  `backup.yml` забирает архив по SSH и отправляет копию. Ответы бота на команды
  идут третьим путём — в теле ответа на сам вебхук (`res.json({method: ...})`),
  поэтому работают без исходящих. Из этого следует ловушка: **рабочий бот НЕ
  доказывает, что исходящие живы** — на этом я и обжёгся 19.09.2026.
- **С сервера бывает не открывается и сам github.com.** 19.09.2026 деплой
  упал на `Failed to connect to github.com port 443 after 129563 ms`, и прод
  застрял на прошлой версии, хотя ветка уехала вперёд. Через семь минут
  тот же деплой прошёл — то есть сеть моргает, а не закрыта совсем.
  Признак: в логе прогона «Deploy to VPS» шаг SSH висит минуты и падает с
  `Process exited with status 128`. Деплой это теперь переживает: git
  пробуется трижды с таймаутом 45 с, а раннер на каждом прогоне кладёт на
  сервер архив с кодом (`/tmp/coco-src.tar.gz`) и разворачивает его, если
  git не смог. **Если правите деплой — не возвращайте серверу роль того,
  кто ходит за кодом сам.**
- **Копию шлёт РОВНО ОДИН источник — расписание `backup.yml`.** Ночной
  systemd-таймер на VPS только собирает и ротирует архив на диске: отправить
  он всё равно не может (наружу хода нет), а доставку не заказывает. Было
  иначе, и получалась петля: `/api/backup/run` при неудачной отправке звал
  `triggerBackup()`, тот запускал прогон `backup.yml`, первый шаг прогона
  выполнял на сервере `deploy/backup.sh`, а он снова бил в `/api/backup/run` —
  и так по кругу. Гасил круг только 30-секундный троттл диспатча, поэтому
  обрывался он не сразу: 22.09.2026 владельцу пришло **пять копий за день**
  вместо одной (01 systemd-цепочка + расписание + три её же повтора).
  Признак возврата болезни: в списке прогонов `backup.yml` подряд идут
  `workflow_dispatch` с интервалом в десятки секунд. Закреплено тестом
  «ночной запуск только собирает архив» в `tests/server.test.js`.
- **`/api/backup/run` не передаёт получателя намеренно.** Если передать,
  сервер каждую ночь будет пытаться отправить файл, упираться в закрытые
  исходящие и писать в `lastBackupError` ложный сбой доставки — диагностика в
  «Кассе» с тех пор всегда выглядела бы красной. Кричать надо о том, что
  архив НЕ СОБРАЛСЯ: это настоящая беда, и пропажа копий на неделю началась
  именно с такого тихого сбоя.
- **Расписание `backup.yml` стоит на 00:30 UTC, а срабатывает около 05:17** —
  GitHub стабильно откладывает его часов на пять. Для копии это неважно, но
  время в Telegram не совпадает с кроном, и это не баг.
- **GitHub молча отключает workflow с расписанием**, если в репозитории долго
  нет коммитов (`state: disabled_inactivity`). 12.09.2026 так разом умерли
  `backup.yml` и `reminders.yml` — копии пропали на неделю, а отсутствие
  напоминаний вообще никто не заметил. Симптом со стороны приложения: запрос
  бэкапа возвращает 422 «Cannot trigger a workflow_dispatch on a disabled
  workflow». Деплой теперь на каждом прогоне проверяет оба и включает обратно
  (нужен `permissions: actions: write`), так что само это больше не всплывёт.
- **Диагностика для владельца — в приложении:** «Игры» → ⚙ → низ блока «Касса».
  Показывает связь с Telegram, свободное место, дату последней копии и причину
  прошлого сбоя. Именно она вывела на 422 после часа гаданий — начинайте
  отсюда, а не с логов.
- Диагностика, не требующая доступа к серверу: workflows «DNS check» и
  «Server check (связь с Telegram)» — оба только читают.

## «Сочность» и редкость в играх — как это устроено

Правила игр не менялись; менялось только то, сколько игра о них рассказывает.

- **Сфера — это СОДЕРЖИМОЕ клетки, наравне с символом и скаттером.**
  `ScatterCell` — это `SlotSymbolId | 'scatter' | \`orb:${number}\``, и
  клетка-сфера рождается там же, где все остальные: в `cell()` движка, когда
  собирается поле. Отдельного списка сфер нет нигде — `gridOrbs(grid)` просто
  читает поле. Сфера едет в ленте барабана (`fillerCell`), встаёт в клетку,
  съезжает вниз при каскаде и блокирует восьмёрки, потому что она и есть
  клетка. **Никаких «свойств» поверх клетки, никакого слоя, никакой подгонки
  координат.** Две прошлые попытки сделали ровно это — сначала отдельный
  абсолютно позиционированный слой, потом поле `orb` в `BoardCell` с
  досыпкой `spawnOrbs` поверх готового поля, — и обе владелец опознал как
  наклейку, трижды повторив просьбу. Признак, что кто-то снова сворачивает
  туда: появляется место, где сфера возникает ПОСЛЕ того, как поле собрано.
- **Своей анимации появления у сферы нет и быть не должно.** Она приходит
  `tumble-fall`, как любая клетка. Клетки поля пересоздаются на каждом такте
  каскада, поэтому разовая анимация появления переигрывалась бы по два раза
  за звено; а главное — ни один символ так не приходит, и собственное
  «всплытие» тут же выдаёт в сфере чужеродный предмет. Приход отмечают звук
  и вибрация (`playOrbs`): они такту перерисовки не подчиняются.
- **Сферы копятся не потому, что их берегут, а потому что убирать их
  нечем.** Они не выигрывают → не попадают в `dead` → остаются в колонке.
  Вся «накопительная» механика — это следствие правил поля, а не отдельный
  код.
- **У `.sboard__col` намеренно НЕТ `overflow: hidden`.** Клипает само поле.
  Верните клипание колонке — и самоцвет при сборе обрежется на её границе,
  когда полетит к счётчику в центре; ровно из-за этого он когда-то и жил
  отдельным слоем.
- **Клетка под сферой в восьмёрку не идёт** — в этом размен: сфера платит,
  но загромождает поле и укорачивает цепочку. Именно поэтому таблица выплат
  может быть выше, чем была бы без этого. Проверяется тестом «закрытая сферой
  клетка не попадает ни в один выигрыш».
- **Сферы срабатывают ОДИН раз, в конце**, умножая весь выигрыш
  последовательности; складываются, а не перемножаются. Падают всегда — и на
  спине, который не сыграл. Раньше они умножали каждое звено отдельно и
  выбрасывались без выигрыша: сферу можно было не увидеть за сотню спинов.
- **`ORB_CHANCE` — шанс отдельной КЛЕТКИ, и отдача почти линейна по нему**
  (≈3 процентных пункта на каждую тысячную). 0,019 даёт ~92% на 300 тысячах
  сессий, сферу примерно в половине вращений, цветную — каждое двенадцатое.
  Меняете — перемеряйте; на глаз тут промахнуться легко, я промахивался.
- **Редкость сфер — в `src/lib/orb-rarity.ts`.** Лестница не придумана, а
  вычитана из таблицы весов `ORB_TABLE` (`lib/scatter.ts`): 66 / 22 / 9 / 2,2 /
  0,6 / 0,2 %. Шансы НЕ менялись — они и так были такими, просто ×2 и ×500
  рисовались одинаковым золотым шариком. `orb-rarity.test.ts` сверяет
  заявленные проценты с настоящими весами, поэтому правка номиналов уронит
  тест, а не пользователя. Верхняя ступень называется «Реликвия» —
  существительное среди прилагательных, оно нарочно ломает грамматику
  лестницы («у меня правила другие»).
- **Бонус должен быть виден делающим работу, а не посчитанным.** Выплата
  идёт в два такта: сначала база, потом сферы слетаются в счётчик, сумма
  тикает вверх и ударом припечатывается — и число растёт на глазах. Пока
  выплата приходила одним готовым числом, множитель существовал только
  внутри выражения. Если трогаете эту часть, держите правило: **строка «что
  сыграло» и счётчик обязаны показывать одну и ту же стадию арифметики**,
  иначе множитель выглядит ни на что не влияющим.

### Подсчёт денег — `src/lib/rollup.ts`

Самая важная сцена спина и та, которую проще всего испортить. Три правила,
и все три нарушались одновременно, пока счёт шёл через `AnimatedNumber`:

- **Длительность ПРОПОРЦИОНАЛЬНА выигрышу и не назначается руками.** Она
  складывается из того, сколько ступеней выигрыш пробил: мелочь считается
  полсекунды, максимум — пятнадцать. Фиксированная длительность (было 400 мс
  в табло, 700 в результате, 1400 в тотеме) — это ровно то, из-за чего
  ×500 проскакивал за то же время, что и ×2, и владелец написал «упала
  сфера 500х… но на деле так быстро всё посчиталось, в общем нет изюминки».
- **Счёт ПРОБИВАЕТ пороги, а не доезжает до итога.** На каждой ступени
  (`WIN_TIERS`) он замирает, звучит удар, меняется титул — и идёт дальше.
  Смотрят именно на «не остановился»; пауза здесь не задержка, а вопрос.
  Со ступени «КРУПНЫЙ ВЫИГРЫШ» сцену забирает тотем, и счёт продолжается
  в нём — **он не начинается заново**, это тот же ход на крупном плане.
- **Темп РОВНЫЙ.** `easeOutCubic` (как было) разгоняется и тормозит к концу:
  старшие разряды пролетают, последние копейки ползут. Механический ролл-ап
  не ускоряется — он идёт как счётчик на бензоколонке.

Ещё из важного:

- **Сочность счёта даёт ТЕМП, а не форма цифр.** Я потратил заход на
  механический одометр — колесо с цифрами 0…9 на каждый разряд — и владелец
  забраковал его одним словом: «цифры такие себе». Он прав, и причины две.
  При непрерывном ходе колеса на экране постоянно висит ПОЛОВИНКА цифры: на
  62 пикселях это механика, на восемнадцати — рваный текст. И каждому колесу
  нужен свой `overflow: hidden`, а он обрезает свечение — вокруг каждой
  цифры вырастает своя светящаяся прямоугольная коробка, и число
  рассыпается на плитки. **Не возвращайте колёса.** Цифрам достаточно быть
  крупными, целыми и читаемыми на любом кадре (`components/MoneyCounter`).
- **Счётчик обновляется через ref, а не через состояние.** Счёт идёт каждый
  кадр; гнать его через `setState` — значит перерисовывать полстраницы
  шестьдесят раз в секунду. `runRollup` пишет прямо в `textContent`.
- **Множитель — ЖЕТОН, а не надпись.** У `.stamp` своя оправа: тёмная плита
  в золотой рамке, подпись «выплата» и число под ней, а поле под жетоном
  гаснет (`.sboard__veil`). Светлая цифра поверх светлых символов не
  читалась вовсе — самый важный момент спина проходил мимо глаза. Градиент
  ступени живёт на `.stamp__n`, а не на самом жетоне: `background-clip: text`
  на жетоне съел бы оправу.
- **Удар множителя обязан сыпать монеты.** Раньше в этот кадр менялось
  только число, и «начислилось» было не видно. Количество монет — по
  сложившемуся номиналу: ×3 это горсть, ×200 — ливень.
- **Баланс крутится в один ход с выигрышем.** Деньги прибывают на глазах,
  а не начисляются задним числом.
- **Счёт обязан быть пропускаемым.** Тап по автомату или по тотему
  досчитывает мгновенно. Без этого крупный выигрыш становится наказанием
  ожиданием — особенно в автоспине и бонусе.
- **Редкая сфера (beats ≥ 2) получает сольный выход** перед сбором: поле
  гаснет, камень выходит крупно и назван по имени. Ступени ниже выходят
  молча — выход, который случается каждый второй спин, это уже не выход.
- Счёт **один на обе игры** нарочно. Если считать по-разному, одна из игр
  ощущается дешевле другой.
- **`src/lib/juice.ts` — приёмы, а не библиотека.** Стоп-кадр (пауза читается
  как удар, её длина — как сила), кадр-вспышка (прячет склейку: всё, что
  меняется во время вспышки, читается как ею вызванное), тряска по Айзерло
  (копится «травма», смещение ∝ её КВАДРАТУ, гладкий шум вместо
  `Math.random` — случайное число на кадр выглядит как сломанный телевизор).
  Трясётся корпус автомата, а не страница: внутри Telegram дёрганье всего
  экрана читается как баг вебвью.
- **Падение клетки: НИКАКОГО перелёта.** `tumble-fall` (обе игры) долго ехал
  на пружине `cubic-bezier(.34,1.34,.5,1)`. Пружина выносит клетку примерно
  на 3,7% ПУТИ ниже её гнезда и возвращает обратно: на падении в пять рядов
  это тринадцать пикселей — символ заезжает в чужую клетку и отскакивает.
  Владелец описал это дословно: «некоторые символы прыгают и возвращаются на
  место». Все четыре контрольные точки кривой обязаны лежать в [0,1] — тогда
  перелёт невозможен в принципе, а не «почти незаметен». Пружина хороша для
  жетона и титула (они одни в кадре), но не для тридцати клеток сразу.
- **Падение — свободное: время ∝ КОРНЮ из высоты, разгон квадратичный.**
  `--fk = √(dy / рядов)` считает страница, длительность `--dur · --fk`,
  кривая `cubic-bezier(.11,0,.5,0)` — это ровно y = t². Так под одной
  гравитацией падает всё, и отсюда главное: клетки одной колонки, сорвавшись
  разом, держат дистанцию, пока нижняя не сядет. Две прошлые формулы этого
  не давали: сначала все летели ровно `--dur` (ближняя ползла, дальняя
  телепортировалась), потом линейно `0.55 + 0.09·dy` с кривой ease-in-out —
  клетка парковалась, как лифт, а в середине падения верхняя налезала на
  нижнюю на треть клетки. Самое длинное падение (все ряды) длится ровно
  `--dur`: иначе клетка не успеет сесть до следующего звена.
- **Приземление — сплющиванием от дна, а не отскоком** (`tumble-land`, второй
  анимацией на той же клетке, `transform-origin` у нижнего края). Клетка ни
  на пиксель не заходит к соседу снизу — правило «никакого перелёта» цело, —
  а вес у удара появился. Сила ∝ `--fk`: с одного ряда еле видно.
- **Поле пересобирается ОДИН раз за спин, а не на каждом звене.** В `runStep`
  стоял `setBoard(gridToBoard(step.grid))` для каждого `i` — а на экране уже
  стоял результат прошлого схлопывания, и он в точности равен `step.grid`
  (движок берёт следующее поле из `step.next`). Лишняя пересборка меняла всем
  тридцати клеткам React-ключ, то есть уничтожала и создавала заново тридцать
  span'ов с картинками ровно в тот кадр, когда начинают играть рамки
  выигрыша. Признак, что кто-то вернул это обратно: `gridToBoard` вызывается
  без проверки `i === 0`.
- **Под `filter` нельзя анимировать НИЧЕГО.** Правило «не анимируем `blur()`»
  знали все, а это — его обратная сторона, и на ней я обжёгся. `filter` на
  родителе (у нас `blur(1.4px)` на `.sboard__strip` во время вращения)
  заставляет браузер растеризовать ВЕСЬ его поддеревом в одну текстуру.
  Пока внутри неподвижно, текстура считается один раз за спин, а вращение
  идёт трансформом — композитор двигает готовый слой. Но одна бесконечная
  анимация внутри протухает текстуру каждый кадр: лента перерисовывается и
  переразмывается целиком. У сфер таких анимаций было две — `orb-throb` на
  каждом камне и `orb-ring` у эпической и выше, — и владелец описал это
  так: «когда барабан крутится и там есть сферы, всё прыгает, а когда сфер
  нет — крутится чётко». Гасим именно АНИМАЦИИ, а не эффекты: статичные
  `drop-shadow` и конический градиент попадают в ту единственную
  растеризацию и в движении не стоят ничего.
- **⚠️ НЕЗАКРЫТОЕ: та правка выкачена, но НЕ подтверждена.** Механизм выше
  верен сам по себе, а вот что чинит он именно этот симптом — не доказано.
  Замер на 24 спинах до и после: 14,79 → 14,25 длинных кадров (>32 мс) на
  спин, p95 34,8 → 33,4 мс. Это шум; упал только худший кадр (117 → 67 мс),
  а это одно наблюдение. Контрольной группы «без сфер» получить не удалось:
  в 48 замеренных спинах сфера в ленте была всегда (при `ORB_CHANCE` 0,019 и
  ленте на 114 клеток это ожидаемо — пустая лента примерно в одном спине из
  девяти). Попытка сделать контроль, выкинув клетки-сферы из DOM руками,
  была ошибкой: этими узлами владеет React, и следующий рендер ломается —
  прогон завис. **Стенд, скорее всего, просто слеп:** headless Chromium в
  контейнере рисует софтверно, и полтора десятка просевших кадров за спин
  могут быть его собственным потолком. Проверять надо на живом телефоне.
  Если симптом остался, следующий шаг радикальнее и требует решения
  владельца: **убрать `blur(1.4px)` с ленты во время вращения совсем** —
  именно `filter` превращает всю ленту в один тяжёлый слой, но размытие там
  стоит за ощущение скорости, и потерю надо оценивать глазами.
  С v2.44.0 размытие живёт только на ровном ходу (см. «Барабаны» ниже), то
  есть под `filter` лента проводит меньше половины вращения — у первой
  колонки «Каскада» 350 мс из 780 вместо всех 780. Подтверждения на
  телефоне по-прежнему нет.
- **Бюджет кадра.** Анимируем только `transform` и `opacity`. **Никогда не
  анимируем радиус `blur()` и параметры градиента** — это перерисовка всего
  кадра. Вращающийся `conic-gradient` рисуется один раз и крутится
  трансформом; это главная ошибка в этой категории на мобильных. Дорогие
  слои (орбита, лучи, радужный перелив) включены только у ступеней, которые
  встречаются меньше чем в 1% случаев.
- **Эскалация обязана быть неравномерной.** Редкое отличается от обычного не
  цветом, а числом тактов: лишняя пауза, отдельный звук, своя вибрация. Если
  показывать легендарную сферу тем же способом, что и обычную, она перестаёт
  быть легендарной. По той же причине лучи за тотемом крутятся только на
  мега-выигрыше.
- Всё перечисленное выключается под `prefers-reduced-motion`.

### Барабаны — `src/lib/reel-motion.ts`

Вращение обеих игр — один план на ленту, проигрываемый через
`Element.animate`. Замер на стенде показал, что было сломано, и все пункты
ниже — ответы на конкретные цифры, а не вкус:

- **Была одна кривая `(.18,.76,.24,1.06)` на всё вращение.** Она стартует
  вчетверо быстрее средней скорости и тормозит всё остальное время: первая
  колонка «Каскада» проходила 90% пути за 400 мс из 780 и дальше ползла,
  всё ещё размытая. Пик — 78 px за кадр, больше клетки: символы стробили.
- **Теперь пять фаз:** замах назад на 0,12 клетки → квадратичный разгон →
  РОВНЫЙ ход → торможение с проездом на 0,16 клетки → возврат в гнездо.
  Кривые подобраны по наклонам на концах, скорость на стыках непрерывна —
  это проверяет тест, а не глаз.
- **Скорость ровного хода ОДНА у всех барабанов обеих игр**: 0,024 клетки/мс
  (≈0,4 клетки за кадр — быстрее глаз теряет направление). Путь ленты
  считается ИЗ длительности. Раньше путь был общий, и поздний барабан просто
  ехал медленнее раннего — шесть колонок в середине спина стояли почти
  одинаково, и поочерёдной остановки не было видно.
- **Лента стартует с того, что на поле.** В «Каскаде» первые клетки ленты
  были случайными: в первый кадр каждого спина всё поле 6×5 подменялось.
  Страница держит `shownGrid` — что стоит на экране прямо сейчас (после
  каскада и после досыпки на место сфер тоже), — и с него строит ленту.
- **Голова и хвост ленты обязательны**: замах открывает клетку над окном,
  проезд — под ним. В «Каскаде» хвоста не было, и на отскоке снизу мигала
  пустая полоса.
- **Длинное вращение идёт по петле.** Предвкушение бонуса тянет колонку
  секунды по три; при одной скорости лента выросла бы до сотни клеток.
  Участок пролёта повторяет в конце своё начало, и лента на ровном ходу
  прыгает назад на длину петли — в окне в этот миг то же самое (кадры с
  одинаковым `offset`). Потолок — 48 клеток пролёта.
- **Размытие — только на скорости**, звук остановки — в момент, когда
  символы дошли до гнёзд (`impact`), а не после отскока.
- **Покой — инлайн-стилем, не заливкой анимации.** Законченная анимация с
  `fill: forwards` числится у элемента, и стоп-кадр (`hitStop`) перезапускал
  бы её: запуск законченной анимации перематывает её в начало, и поле
  закрутилось бы ещё раз. Сам `hitStop` теперь трогает только анимации
  в состоянии `running` — до этого он точно так же переигрывал упавшие
  клетки, жетон и титул на каждом ударе во время счёта.

### Слияние сфер пузырями — `src/lib/orb-merge.ts` (v2.45.0)

Запрос владельца: «если на поле больше одной сферы, пусть объединятся в
одну, анимация как мыльный пузырь, много вариантов, продумай турбо».

- **Только в такте сбора, правила не тронуты.** Сферы по-прежнему лежат
  клетками до конца цепочки и срабатывают один раз; слияние — это то, КАК
  они собираются в финале, когда сфер ≥ 2. Одна сфера улетает в жетон, как
  раньше. Слить сферы посреди каскада значило бы освободить клетки под
  восьмёрки — это уже другая отдача, а не анимация.
- **Двигаются сами клетки, а не наклейки.** План считает путь каждой
  клетки-сферы, страница проигрывает его `Element.animate` на самой клетке.
  Число на общем пузыре — это id клетки (`orb:${сумма}`), поэтому цвет
  ступени растёт вместе с суммой: три обычные ×4 на глазах становятся
  «редкой» ×12. Кольцо эпической появляется, когда сумма до неё доросла.
- **Шесть вариантов** (`MERGE_VARIANTS`, выбор случайный по весу): к центру,
  к старшей, снежный ком, парами, вихрь, всплытие. В турбо — только первые
  два и «парами»: цепочка переходов, сжатая по времени, превращается в
  мельтешение. Время сжимается на ту же долю, что и весь каскад (0,55), и
  упирается в потолок: 2,8 с обычно, 1,5 с в турбо.
- **Порядок слияний не бывает кучей**: между двумя «блоп» — не меньше
  `gapMs`, каждое слышно и видно отдельно. Звук растёт тоном
  (`bubbleMerge(k)`), общий пузырь раздувается по объёму (кубический
  корень), но не больше ×1,6 клетки.
- **Пузырь — внутри тела сферы** (`.orb__body`). Клетку двигает план, тело
  колышется от ударов (ось — откуда влился поглощённый), поглощаемый
  вытягивается к цели. Два трансформа на одном элементе дрались бы — отсюда
  обёртка. Камень внутри пузыря уменьшается свойством `scale`, а не
  `transform`: трансформ у камня занят его «дыханием».
- **Плёнка переливается прозрачностью** двух неподвижных конических слоёв с
  маской кольца. Не вращением: вращать внутри скруглённого overflow корпуса
  нельзя (см. «Купальскую ночь»).
- **Масштаб — от центра.** У упавшей клетки `transform-origin` внизу (она
  сплющивается о дно), и раздутый пузырь уезжал на пол-клетки вверх — общий
  лопался мимо жетона. Правило `.sboard.is-merging .sbcell--orb`
  возвращает центр; то же нужно было и старому полёту в жетон.
- **Безопасная зона**: план держит раздутый пузырь целиком в поле — сфера из
  крайней колонки при надувании отходит от кромки внутрь.
- **В бонусе** жетон с прошлым множителем уже стоит посередине. Пузыри
  сходятся и лопаются выше него (`stampShown`), иначе последние полсекунды
  общий висел бы под жетоном невидимым.
- **Лопание — склейка под вспышкой.** Плёнка расходится кольцом, брызги
  летят, камень уходит в точку, и через 70 мс ударом встаёт жетон с полной
  суммой (прежний `slam`: вспышка, монеты, тряска). Досыпка поля ждёт брызги.
- **Тап по автомату дожимает слияние** (`mergeSkip`): все пути доигрываются
  мгновенно, пузырь сразу лопается. Слияние обязано быть пропускаемым, как и
  счёт.
- Под `prefers-reduced-motion` слияния нет — сразу прежний сбор без
  движения.
- Тесты `orb-merge.test.ts`: ровно n−1 слияний и полная сумма в конце,
  поглощённый доплывает ровно до поглотившего и гаснет только у цели, никто
  не срезан кромкой, потолок времени, в турбо только быстрые варианты.

### Остальное, что поправлено в той же шлифовке (v2.44.0)

- **Сбор сфер синхронен с прилётом.** Счётчик прибавляет номинал сферы в тот
  кадр, когда она коснулась жетона (`ORB_ARRIVE` = 0,86 полёта — та же доля
  в CSS `orb-fly`), удар — после последней. Раньше сумма тикала полсекунды
  по часам, и при пяти сферах удар звучал, пока четыре были в воздухе.
  Жетона нет, пока не долетела первая: «×0» посреди поля — шум. Летящая
  сфера — над вуалью (`z-index` 5), под жетоном. После удара поле
  схлопывается на места сфер, как после выигрыша (`dropHoles`), а не
  досыпает символ из соседней клетки сверху.
- **Жетон «Каскада» наконец входит.** `.stamp.is-collect` целиком заменял
  анимацию жетона, и вход не играл вовсе. Уходит жетон с вуалью тоже
  анимацией (`is-out`), а не одним кадром.
- **Вуаль сбора лежит уже под сольным выходом** — иначе между соло и сбором
  проскакивал светлый кадр.
- **Оверлеи уходят, а не обрываются** — `lib/use-exit.ts`: тотем и плашка
  уровня; состояние страницы уже `null`, разметка доигрывает уход.
  Затемнение поля при выигрыше живёт всегда и гаснет прозрачностью.
- **`@keyframes combo-in` были потеряны в v2.35.0** — плашка цепочки
  возникала одним кадром. Строка «что сыграло» (`.hits`) использовала те же
  кадры, но центрирована иначе — у неё свои `hits-in`, иначе она уезжала бы
  на полширины.
- **«Слоты» трясутся и бьют тем же `juice.ts`, что «Каскад».** CSS-тряску
  снимал `onAnimationEnd` на корпусе, а он всплывает от каждой дочерней
  анимации: первая упавшая клетка обрывала тряску посреди размаха. Рычаг
  дёргается и от кнопки «Крутить».
- **Вспышка открывающего удара — только у церемонии** (от «ХОРОШЕГО»): её
  работа — спрятать сброс счётчика на ноль, а мелкому выигрышу сбрасывать
  нечего. Раньше экран мигал на каждом «ВЕРНУЛОСЬ».
- **Линии выплат.** Общий `stroke-dasharray: 200` при
  `vector-effect: non-scaling-stroke` меряется в пикселях экрана — V-линия
  (~350 px) обрывалась, правого плеча не было. Длину штриха страница считает
  по каждой линии; `pathLength` с non-scaling-stroke в Chromium делит неверно.
- **Колесо удачи.** Кривая стартовала на 47° за кадр — ровно сектор, и
  восемь секторов на такой скорости стояли или мерцали (эффект колеса в
  кино). Теперь замах, разгон до ~19° за кадр и долгое торможение. Щелчки
  — по секторам, прошедшим под язычком (редеют вместе со скоростью), язычок
  качается. Тень — отдельным неподвижным слоем: `drop-shadow` на самом диске
  крутилась вместе с ним.
- `AnimatedNumber` при смене цели посреди хода больше не прыгает назад:
  новый ход стартует с показанного значения. Монеты дождя падают с
  ускорением, а не тормозят у низа экрана. Вспышка взрыва выигрышной рамки —
  слоем по прозрачности вместо `filter: brightness()` в кадрах.

## Кузница v2.67 — сила кирки, твёрдость руды, редкость (ЧИТАТЬ про кирку)

Владелец: «для перехода всего по одному цельному блоку — мало», «лагерь,
улучшение кирки, заказ — ужасно, непонятно, отталкивающе; возьми пример у
популярной игры», «нахер кирке урон», «чем круче кирка, тем ярче —
легендарная, не легендарная». Решения по плану (`docs/plan-kuznica-2026-09.md`):
твёрдость руды — да, круг A→Z — 4–5 ч у идеального игрока.

- **Кирка называется по руде, ИЗ которой куётся, и открывает следующие
  этажи** (Майнкрафт, Terraria): Железная — из железа на G, берёт H–I
  (кобальт). Ворота этажей — D, F, H, …, X, Y, Z; кирка №N куётся на своём
  этаже-материале (`floor`) и нужна для `floor + 1`. `rockHardness`,
  `pickPower`, `canMine`, `minPickFor`, `opensRocks` — в `prison.ts`.
- **Твёрдость — УСЛОВИЕ РАНГА, а не «после ранга поле звенит».** Так было в
  плане, и так делать нельзя: шахта — яма, твёрдый верхний блок закрывает
  всё под собой, и новый этаж без кирки выкапывался бы на ~16%, после чего
  игрок уходил бы на этаж назад. Поэтому ранг просит кирку под следующий
  этаж (`rankNeeds().pickOk`), а «звенит» руда следующего этажа на ДНЕ
  (`NEXT_ROCK_CHANCE` 5%): она ничего под собой не закрывает и показывает,
  за какой киркой идти. Тест «руда следующего этажа звенит только на дне».
- **Звон — в `useMineDig`, а не в странице**: `DigRules.hard(c)` возвращает
  нужную силу, удар по такой клетке — звон, искры, «⛏N» и `onHard`;
  `breakCells` и Трещина твёрдые клетки пропускают. Стор тоже не ломает
  руду твёрже кирки (`prisonBreak`) — не полагаемся на честность страницы.
- **Урона и заточки нет для игрока.** У кирки «Сила ⛏» и «Скорость»
  (`pickSpeed` — блоков в минуту на удержании по составу ЭТОГО этажа,
  только ударами: взрывы и жилы — случай, а не скорость). `dmg` остался
  внутренним числом. Чара «Сила» переименована в «Эффективность» (id тот
  же, `power`), Уруз и росомаха — «к скорости копки», Райдо и оленёнок —
  «к частоте ударов». Слово «урон» у кирки не возвращать.
- **Заказа кузнице больше нет — есть ЯЩИК КУЗНЕЦА** (`forgeBox`). Руда
  следующей кирки не продаётся: продажа руками и вагонетка сперва кладут её
  в ящик (`reserveOre`, `stash(..., {box, pick})`), в спецзоне руда идёт в
  ящик прямо из-под кирки (`feedBox`). Выковка (`prisonForge`) берёт сперва
  из ящика, потом из рюкзака; монеты — в момент выковки. Цена на кнопке
  «Продать» — БЕЗ руды для кирки; если в рюкзаке только она — «В ящик».
- **Старые сохранения:** оплаченный заказ v2.66 переезжает в ящик и
  помечается `forgePaid` (монеты второй раз не берутся); кирка ниже
  нужной этажу поднимается до `minPickFor(rank)` — иначе поле встало бы
  стеной. Полного сброса («Нового срока») НЕ было.
- **Редкость — `lib/rarity.ts`**, одна лестница на кирки (потом книги,
  топоры): Обычная (Ржавая–Кованая) → Необычная → Редкая → Эпическая →
  Легендарная (Алмазная, Звёздная) → Мифическая → Божественная

### Дверь логова (v2.66)

«Победил короля, но уйти не могу — дверь исчезла, будто скрытая».
Клетка ворот не входит в арену: шаг на неё = «вышел» → король «отдыхает»
→ ворота закрывались прямо на герое, его выталкивало обратно, они снова
открывались. Со старой логикой бот выходил 0 раз из 200. Теперь победитель
помечен `exiting`, и ворота закрываются, только когда он отошёл дальше
`GATE_CLEAR` (2,5 клетки); снаружи к отдыхающему королю они по-прежнему не
пускают. Тест «после победы из логова выходят…» — 200 выходов.

  блока, и без этого поздние ранги превращались в стену. Меняете цены,

- **Запал — серия копания, как Momentum на присонах.** Каждый сломанный

### Лесоповал, Л1 «Делянка» (v2.52.0) — `lib/forest.ts`, `pages/ForestPage.tsx`

Владелец: «в Присоне можно было не только копать в шахте, но и рубить
дрова… чтобы также затягивательно, как и с шахтой». Выбран вариант «вид
сбоку, ритм лево/право» — владелец одобрил его против сетки сверху.

- **Лес — НЕ перекрашенная шахта.** Шахта — «держи и веди» сверху, лес —
  «ритм и реакция» сбоку (как Timberman). Одно дерево, ствол из брёвен,
  сучья слева или справа. Тап по стороне рубит нижнее бревно с неё.
  Сучок бьёт по лбу в двух случаях (`standHit`, `dropHit`): встал туда, где
  сучок у нижнего бревна, или срубил — и на твою сторону опустился сучок
  следующего. Удар: оглушение 0,7 с и запал в НОЛЬ. Умереть нельзя.
- **Дерево обязано быть решаемым.** Первая сборка ставила на СОСЕДНИЕ брёвна
  сучья с разных сторон — тогда увернуться нельзя в принципе (слева упадёт
  следующий, справа налетишь на нижний), и стенд застревал на пятом бревне.
  Правило генератора: сразу за сучком с одной стороны — только сучок с той
  же стороны или пустое бревно. Тест «у каждого бревна есть безопасная
  сторона» гоняет все делянки.
- **Десять делянок — кольский лес**: ива → ольха → осина → берёза → рябина →
  сосна → ель → лиственница → можжевельник → карельская берёза. На делянке
  65% своей породы, остальное — прошлая, изредка — следующая (подсказка).
- **Разряд лесоруба = делянка** (с v2.66 делянку ещё и открывает ранг
  шахты, `PLOT_GATE`: ива C … карельская берёза X), за общие монеты плюс **план в кубометрах**
  (1 бревно = 0,1 м³) своей породы — та же механика, что норма шахты, и тот
  же откуп недобора. Лестница независима от шахты, но открывается с ранга C
  (`FOREST_UNLOCK_RANK`): сначала шахта.
- **Особые брёвна**: свиль ×3, капокорень ×10 (только комель), дупло (слеза
  гаста, передачка или токены), чага (только на берёзах — токены). **Сейд-
  сосна** — одно дерево из тридцати: светится, брёвен ×1,6, каждое платит
  токенами, повал — пачкой токенов.
- **Топоры и пилы**: ржавый → плотницкий → лесорубный → колун → лучковая пила
  → бензопилы «Дружба» и «Урал» (у пил свой звук и силуэт). Правка лезвия,
  штабель (рюкзак леса) и лесовоз (вагонетка) — вкладка «Топоры» в лагере.
- **Общее с шахтой**: кошелёк, токены, ключи-слёзы (выпадают сценой тотема —
  она теперь в `lib/totem.ts` для обеих страниц), передачки (зреют и от
  брёвен), питомец (растёт и от брёвен), руны и перки (через `forestMods`).
  Чары кирки топору НЕ передаются — у топора будут свои в Л2. Запал — те же
  ступени, что в шахте, счёт брёвнами.
- **Своё сохранение** (`forest.state`) — чтобы шахта не распухала. Сбросы
  из настроек обнуляют и лес. Урон по бревну живёт в странице, в стор идёт
  только срубленное (`forestCut`), пишется с задержкой 2 с, как шахта.
- **Темп проверен тестом** `forest.test.ts`: на одном лесе вся лестница ≈ 1 ч,
  первый разряд за ~1,5 мин, самый долгий — 18 мин, план ощутим почти на
  каждом разряде. Сначала сделал разряды ×2,05 — вышло 2,4 ч и 40 мин на
  последний; лечилось ценой пород (рост 1,42) и шагом разряда (1,8).
- **Стенд**: после правки `lib/*.ts` Vite отдаёт странице модуль под новым
  адресом, и скрипт стенда пишет в другой экземпляр стора — перезапускайте
  dev-сервер. И не пишите `pkill -f` с текстом, который есть в самой команде:
  убьёте собственную оболочку.

### Лесоповал, Л2 «Лесопилка» (v2.53.0)

- **Чары топора — свои** (`AXE_ENCHANTS`): Щепа (лишние брёвна), Живица
  (токены), Чутьё (увернуться от сучка + опасный сучок светится), Замах (два
  бревна разом), Валка (дерево с одного удара), Бурелом (падающее дерево
  валит соседнее целиком). Платятся ОБЩИМИ токенами — шахта и лес тянут из
  одного кармана, и в этом выбор. Уровень топора = `axeLevelOf(logs)`: та же
  кривая, что у кирки, но бревно даёт 3 опыта (рубится дольше блока).
  Открытие и потолок — как у кирки: к 40-му уровню всё.
- **Сколько брёвен уходит ударом, решает `planCut`**: валка первой (редкая,
  перекрывает замах; на двух последних брёвнах ей валить нечего), бурелом —
  только если дерево упало. Каждое бревно удара бросает свою добычу
  (`rollChop`), и все идут в план: замах и валка — это топор, а не добыча.
- **Пилорама пилит по часам, а не по кадрам.** `millTick(mill, now)` —
  чистая функция: стор досчитывает перед каждым действием, страница — для
  показа. Дробь распила переносится, пустая очередь её обнуляет. Очередь —
  на 2 часа работы: пилит без тебя, но не бесконечно. Дорогие породы вперёд.
- **В пилораму уходит «голая» цена пород** (`pile.sp` — брёвна по породам,
  появилось в v2.53; старый штабель считается породой своей делянки).
  Надбавка за свиль, капокорень и дрова с кроны платится сразу при загрузке:
  пилить её не нужно, а в очереди она бы потерялась.
- **Лесовоз везёт полный штабель на пилораму**, пока там есть место, иначе
  продаёт. Так пилорама работает сама, а не требует лишнего тапа.
- **Пилорама обязана окупаться и БЕЗ офлайна.** Первая версия (6 брёвен в
  минуту за 2 500) в симуляции делала лестницу ДЛИННЕЕ: деньги уходили, а
  пилила она долю того, что рубишь. Скорость подобрана под топор: первая
  успевает за ржавым, шестая — за «Уралом». Тест «чары топора и пилорама
  ускоряют лестницу» держит это правило.
- **Мосты в шахту**: крепь (20 любых досок → расходник `prop`, 10 минут
  Перековка +50%) и рукояти (берёза / лиственница / карельская, 40–80 досок
  своей породы, +3/6/10% к скорости кирки И топора; следующая заменяет
  прошлую). Рукоять живёт в `prison.handle`, потому что её читает `modsOf`.
  Крепь в лавке не продаётся (цена 0 → лавка её прячет), в ряду расходников
  шахты появляется только с пилорамой.
- **Доски на следующую рукоять отложены**: «Продать доски» их не трогает, а
  крепь берёт из запаса в последнюю очередь (`boardsReserve`, `takeBoards`).
  Иначе одна кнопка продажи съедала бы то, что копишь на рукоять.
- Темп: с чарами и пилорамой вся лестница ≈ 0,9 ч (без них 1,03). Деньги от
  досок в план не идут, поэтому план стал отставать сильнее (до 1,5 цены
  разряда) — доля плана снижена 0,85 → 0,75.

### Правки леса после проверки владельцем (v2.56.0)

Владелец: «когда рублю и тыкаю вправо или влево, бывает задержка»,
«лагерь в шахте должен быть про шахту, а не про лесополосу», «что мы
отправляем в лесопилку — непонятно, не хватает интерактивности».

- **Тап на делянке никогда не теряется.** Причин задержки было три: падающая
  крона глушила ВСЕ тапы 0,9–1,4 с после каждого дерева (`falling`), тап
  чаще раза в 185 мс (ржавый топор) молча выбрасывался, а новое дерево
  0,37 с стояло невидимым и ещё 0,45 с въезжало. Теперь глушит только
  оглушение сучком; ранний тап встаёт в очередь (`pendingTap`) и бьёт, как
  только топор вернулся; дерево въезжает за 0,26 с. Топор переставляется
  на сторону прямо в DOM (`placeAxe`), в том же кадре, что и замах, — не
  ждёт перерисовки React. На стенде 40 тапов подряд через 90 мс = 40
  срубленных брёвен при трёх поваленных деревьях.
- **Лагерь у шахты и у леса — разный** (`PrisonCamp place`, `PLACE_TABS`).
  В шахте: кузница, чары, руны, питомцы, лавка, сундуки, бригада,
  коллекция, вехи, перки. В лесу: топоры, чары (топора — отдельной
  вкладкой), лесопилка, а общее — сундуки, питомцы, руны — стоит после
  лесного. Двор открывает лагерь по зданию и держит место (`campPlace`):
  общая вкладка не перебрасывает лесной лагерь в шахтный. Крепь с пустым
  запасом в шахте теперь говорит, что её сбивают в лесу, а не открывает
  лесопилку в шахтном лагере.
- **Пилорама — сцена, а не цифры** (`MillScene`): слева брёвна в очереди,
  по ленте они едут в диск, справа выходят доски; лента идёт в темпе пилы.
  Кнопка пилорамы на делянке больше НЕ отправляет штабель молча — она
  открывает эту сцену, и штабель грузят кнопкой «Штабель → в пилу» с
  объяснением, что ушло и что заплачено сразу. **Тап по диску подаёт бревно
  рукой** (`millFeedOne`, `forestMillFeed`): диск рвётся, опилки, доска
  выскакивает. Выгода от рук упирается в нарубленное, а не в скорость тапа
  — больше, чем в очереди и штабеле, не распилишь.

### Руны, сундуки, верстак, бригада (v2.57.0)

Владелец: руны «нарисованы ужасно и непонятно, и куда они накладываются —
написано просто кирка»; «дай открыть все сундуки разом и суммируй»;

- **«Открыть все» сундуки** (`prisonOpenCases`): по одному подряд в сторе —

- **Верстак — своя вкладка** (`BenchTab`) и у каждой вещи написано, куда

- **Заказы** (`benchOrder`, три места): ящик для рыбзавода, табурет, лыжи,
  бочка под засол трески, оконная рама, сани оленеводу, карбас поморам (с

  продажи тех же досок плюс токены; сдал — новый заказчик через 10 минут.

  `benchTexture` в цвет досок породы; контур у них СНАРУЖИ (`outlineOut`),
  иначе двухпиксельная ножка табурета уходила в чёрное.
- **Бригада — наряды** (`CREW_SHIFTS`): норма (8 ч, ×1), ударная (2 ч,
  ×2,5 — для тех, кто заходит часто), разведка (6 ч, ×0,5, но ключи и
  передачки). Перк «Длинная смена» удлиняет любой. Смена наряда сдаёт
  накопленное по старому. **Пайка** — +30% на всю смену, но только в
  первые 10 минут, иначе кормили бы перед самой сдачей. **Приём смены** —
  вагонетки: тап опрокидывает, доля денег падает в счётчик; в конце —
  находки разведки. Бригада нарисована рабочими у штольни (у каждого своя
  рубаха); кончилась смена — сидят и ждут.

НЕТ — владелец против), длинный цельный мир под лагерем, крысы, мясо Барыге,

`lib/dungeon-world.ts` + карты `lib/dungeon-maps.ts`, бой `lib/dungeon-sim.ts`,
пиксели `lib/dungeon-art.ts`, кадр `lib/dungeon-render.ts`; разметка —
`components/DungeonRun.tsx` (вылазка), `DungeonMine.tsx` (шахта внизу),
`DungeonCamp.tsx` (вкладки лагеря), страница `pages/DungeonPage.tsx`.
Вход — здание «Клеть» во дворе, с ранга F.

- **Мир цельный, пикетов и переходов нет.** Экран загрузки — только клеть
  (спуск и подъём): владелец прямо сказал «без геодезии» и «переключение —
  только когда уходишь». Районы стоят друг на друге снизу вверх, сохранение
  хранит место в МЕСТНЫХ координатах района (`area, x, ly`): добавленный
  снизу район не должен сдвигать всех в стену.
- **С v2.66 цены подземелья постоянные** (`MEAT_BASE`, `AREA_MEAT`,
  `PLUS_FEE`, `REFORGE_FEE`, `KING_COINS`, `SACK_PRICE`, `LIFT_PRICE`;
  `econOf` и насыщение рынка удалены). Пункт ниже — история.
- **Деньги — в «минутах шахты»** (`econOf`): цена мяса, сбор за заточку,
  ремонт клети — доля того, что шахта игрока даёт за минуту. Поэтому
  подземелье весит одинаково на F и на Z. **Монеты ступени не открывают**:
  перековку открывают условия («убить 300 пасюков», «вскрыть 3 шахты») и
  материалы со склада. Иначе занос в автомате проскакивал бы десятки часов.
- **Смерть забирает только сидор.** Убийства, опыт, пройденные метры,
  открытые решётки и фонари остаются всегда: дельта (`takeDelta`) уходит в
  стор раз в 5 с, на смене района, на смерти и на подъёме. Не делайте смерть
  «откатом прогресса» — это работа руками.
- **Вынести добычу — только клетью**, и только починенной (`lifts`). Клеть
  Устья целая, Откатки — чинится внизу за монеты и шкурки со склада (не из
  сидора: он ещё не вынесен).
- **Вылазка живёт в сторе (`run`).** «Назад» Telegram сперва открывает паузу
  (`registerEscape`), из паузы можно уйти наверх без клети — вылазка ждёт
  внизу с тем же сидором; вернувшемуся даётся 2 с неуязвимости осмотреться.
- **Управление:** левая половина экрана — плавающий джойстик (основа там, где
  коснулся, едет за пальцем, мёртвая зона 14%); «Удар» — тап = серия из трёх,
  держать = тяжёлый, смахнуть с кнопки = удар в ту сторону; тап по крысе —
  цель; «Рывок» проходит сквозь укус, рывок в последний миг = замедление и
  гарантированный крит; «Вихрь» копится ударами; кусок мяса лечит, но мясо в
  сидоре пахнет и зовёт крыс. Клавиатура для стенда: WASD, J, K, L, Q, E.
- **Кадр рисуется мимо React.** Мир меряется игровыми пикселями (кадр ≈160
  в ширину), но рисуется СРАЗУ на экранную канву с целым множителем и
  дробной камерой — см. «Тряска» ниже. Куски карты 16×16 клеток в кеше,
  перерисовываются, только если сменилась клетка или трещина получила удар.
  Свет — маска с `destination-out` в маленьком буфере, на экран ложится со
  сглаживанием; глаза крыс рисуются ПОСЛЕ света: в темноте видно, откуда
  лезут. Табло React обновляет не чаще 8 раз в секунду и только при
  изменении.
- **Грабли, на которые я наступил:**
  - Первый кадр `requestAnimationFrame` приходит с меткой РАНЬШЕ
    `performance.now()`: dt < 0, номер кадра позы −1 — и `paintHero` падает.
    Шаг зажат снизу нулём, кадр позы берётся по модулю с плюсом.
  - Разработческий StrictMode снимает эффект сразу после постановки: запись
    на снятии превращала НОВУЮ вылазку в «продолжение». Пишем, только если мир
    успел сделать хоть что-то (`sim.time > 0.3`).
  - Крыса, ждущая очереди в норе (`t < 0`), по формуле выползания уезжала
    НАЗАД в стену и рисовалась на ней. Теперь сидит в норе и не рисуется.
    У падающей со свода при `t < 0` радиус тени был отрицательным — канва на
    `ellipse` бросает исключение.
- **Шахты внизу — наш экран шахты** (`MineField` + `useMineDig`): та же
  кирка, заточка и чары, что в каторге, но добыча — в сидор. Прочность руды
  от породы ранга игрока (`deepHp`): иначе алмазная кирка сдувала бы поле за
  секунды. Поле одно на окно часов (`deepField`), выработка 85% — ждать окна.
  Пока копаешь, мир стоит, но шумишь: каждые 20 блоков у входа собирается
  стая, и выходишь ты к ней (`packAtMine`). Зелёных точек «нужная порода» на
  пирите нет — он виден по рисунку, точки на половине поля ничего не значат.
- **Баланс проверен ботом в тестах** (`dungeon-sim.test.ts`): Устье
  проходимо на +2, Откатка без еды на Т2+0 убивает, на +5 — нет, король на
  Т2+3 падает за 1–4 минуты, на Т1+0 почти всегда побеждает он. Меняете
  урон, здоровье или спавн — тесты скажут, что уехало.
- **Стенд:** в дев-режиме симуляция лежит в `window.__dg`, рисовальщик — в
  `window.__dgr` — бот водит героя настоящими событиями клавиатуры, а
  плавность меряется сдвигом `__dgr.camY` по кадрам. Вагонетка может скатиться по рельсу к
  самому входу в клеть Устья: живой игрок обойдёт её сбоку или отобьёт
  ударом, бота надо вести в клеть сбоку.

#### Правки после проверки владельцем (v2.59.0)

Владелец: «когда передвигаюсь, очень сильно трясёт камеру»; «вышел из
шахты — вокруг очень много крыс»; «рывок — как будто телепортируюсь»;
«очень мало инвентаря… надо как в Майнкрафте, открывать и смотреть броню»;
«прокачка не должна быть „успешно выйти“ — убить крыс, добыть в шахте».

- **Тряска — это были рывки, а не `trauma`.** Две причины сразу. (1) Шаг
  боя был фиксированный 1/60 с накопителем: на экранах 90–120 Гц за кадр
  выпадало то ноль шагов, то два. Теперь шаг — под каждый кадр, длинный
  кадр режется на куски ≤ 1/60 с. (2) Мир рисовался в буфер и растягивался:
  камера и спрайты прыгали ЦЕЛЫМИ игровыми пикселями — это 7 точек экрана на
  телефоне, и сдвиг шёл 7, 7, 14, 7… Теперь всё рисуется на экран с
  масштабом, позиции прижаты к ТОЧКЕ экрана (`q()`), пиксели спрайтов
  остаются ровными квадратами. Замер на стенде: камера идёт ровно по
  8,6 точки за кадр. Упреждение камеры сглажено отдельно и не берёт скорость
  рывка. **Не возвращайте буфер с растяжкой и `Math.round` в игровых
  пикселях** — тряска вернётся.
- **Рывок — выпад на 0,3 с с торможением** (старт втрое быстрее бега, конец —
  скорость бега), 2,5 клетки вместо 3, за ним тают силуэты героя. Мигание
  неуязвимости на рывке ВЫКЛЮЧЕНО: 20 миганий в секунду и читались как
  исчезновение. Неуязвимость 0,27 с из 0,3 — с полной тест «король на
  Лагерном без заточки» проигрывался: выпад стал слишком надёжным.
- **Стаи у шахты:** шум — каждые 35 блоков, не больше трёх стай (2, 3, 3
  крысы). Было каждые 20 и без потолка.
- **Сидор — ячейки как в Майнкрафте** (`sackSlots`, `slotsUsed`,
  `canTake`, `sackStacks`): ряд — 9 ячеек, в ячейке стопка одного вида до
  32 (корона — одна), карманы добавляют ряды до четырёх. Было 60 штук
  всего. Запах мяса остался «каждые 10 кусков»: пробовал ослабить под
  большой сидор — Откатка без еды перестала быть опасной (тест баланса).
  Большой сидор и есть риск: несёшь много — крыс вдвое больше.
- **Инвентарь** (`components/DungeonInventory.tsx`) — кнопка сидора на
  табло, мир стоит. Палитра нарочно майнкрафтовская (серая панель со
  скосами, белые цифры с тенью): владелец просил именно «как в
  Майнкрафте». Тап по вещи на человечке — сила и прогресс перековки
  (с непосланной ещё дельтой вылазки), по ячейке — цена, «съесть»,
  «выбросить». Выброшенное ложится у ног с `age −1,6`: магнит не
  подбирает его обратно сразу.
- **Условия перековки — только убийства и руда.** Каска — «добыть пирита»
  (стат `ore`, пишет шахта подземелья прямо в стор при сломе блока, как
  убийства — прогресс не пропадает при смерти). «Выйти живым» из условий
  убрано совсем; тест держит, что его там нет.

#### Спрайты, разведка, прокачка внизу (v2.60.0)

Владелец: «анимация ходьбы и предметы в руках выглядят ужасно… поищи, откуда
скопировать пресеты и сделать топ»; «чтобы не было тумана войны, или если я
один раз прошёлся — туман исчезал»; «качать вещи можно прям в подземелье».

- **Герой и клинки — из Ninja Adventure Asset Pack** (Pixel-boy, лицензия
  CC0; лежит в `public/dungeon/na/`, источники в `CREDITS.txt`). itch.io и
  opengameart сеть не пускает — набор взят зеркалами на GitHub. Код —
  `lib/dungeon-sprites.ts`. Лист персонажа 64×112: столбцы вниз/вверх/влево/
  вправо, строки 0–3 шаг, 4 удар, 5 прыжок, 6 особые позы. Эффекты — листы
  высотой 32, кадр 32, хвост листа бывает пустым (`FX_FRAMES`).
- **Ступень робы = персонаж набора, ПЕРЕКРАШЕННЫЙ по ролям цветов** (мех,
  ватник, каска, броня, кожа), а не по яркости: Т1 — северянин в капюшоне
  (ушанка), Т2 — солдат в каске (шахтёрская каска с лампой), кованые Т3/5/7 —
  рыцарь в шлеме, остальные — рыцарь в плаще. Две грабли: у первого
  персонажа кожа красно-оранжевая, и серый ватник с серым лицом читался
  мешком (кожа теперь общая, `SKIN`); оранжевая каска на оранжевом лице
  читалась чёлкой, отсюда жёлтая каска и **тёмная лампа с ярким стеклом**,
  которую код дорисовывает в каждый кадр, где видно лоб. Проверять ступени
  листом крупно (все 8 × 4 стороны), а не по одной.
- **Клинки набора нарисованы остриём ВНИЗ**, навершием вверх: удар по
  умолчанию у них — к зрителю. Я сперва решил наоборот, и в руке был
  «молоток». Поворот — `угол − π/2`, рукоять в кулаке.
- **Шаг — по пройденному пути** (`h.walk / 0.36` клетки на кадр): ноги не
  скользят ни на какой скорости. Сторона выбирается с запасом (`dir4`),
  иначе по диагонали герой мигал бок/спина. Клинок виден ТОЛЬКО в ударе,
  наборе и вихре; в покое его нет. Кулак — по ходу удара от груди; при
  наборе тяжёлого клинок уходит за плечо, иначе висел поперёк лица.
- **След удара — серп набора**, а не нарисованная дуга: смотрит вправо и
  идёт снизу вверх; поворачиваем на угол удара и отражаем, когда удар идёт
  сверху вниз (первый удар серии). Третий удар — двойной серп, тяжёлый —
  тройной, вихрь — круг. Попадание — звезда, крит — крест, убийство — клуб
  дыма (мелкий и полупрозрачный: четыре крысы одним ударом сливались в
  кляксу поверх мяса), уклон — кольцо, уровень — кольцо со звездой, взрыв —
  пламя. Мясо частиц (`burst`) осталось — оно и есть «сочность».
- **Пока картинки не пришли, рисуется прежний герой** (`spritesReady`), и
  все эффекты откатываются на старые кольца: `addFx` возвращает false.
  Загрузка начинается в клети (`useDungeonSprites`), портреты в лобби,
  клети, лагере и сидоре перерисовываются, когда картинки пришли.
- **Разведанное — светлым, навсегда.** Биты разведки (`sim.fog`, радиус 5)
  были и раньше, но свет их не читал. Теперь `cutExplored` вырезает темноту
  на 82% (`EXPLORED_LIT`) по маске «точка на клетку», растянутой со
  сглаживанием: край разведанного плавный, а не лесенкой 16×16. Не 100% —
  фонарю героя и лампам остаётся работа. Для будущих тёмных районов
  («Тёмный горизонт») долю, скорее всего, придётся сделать районной.
- **Заточка, перековка и карман — прямо из инвентаря в вылазке**
  (`dungeonUpgradeHere`, `dungeonSackUpHere`). Материалы — сперва склад
  лагеря, недостающее из сидора (`payFromBoth`); монеты — общий кошелёк.
  Два обязательных шага вокруг платежа: ДО — `save()`, чтобы убийства и
  руда этой вылазки попали в стор (условия перековки читают стор); ПОСЛЕ —
  пересчёт героя (как при новом уровне) и снова `save()`: сидор уже отдал
  материалы, и перезапуск не должен их вернуть из старого снимка.
- Карман в лагере больше не требует «сперва выйди из вылазки»: ждущая внизу
  вылазка собирает мир заново из стора и возьмёт новый размер сидора.

#### Окружение и крысы (v2.61.0)

Владелец: «маленькая, графика ужасная, ищи пресеты, сделай шедевр. Также с
мобами». Файлы: плитки `lib/dungeon-tiles.ts`, кадры атласа
`lib/dungeon-x72-frames.ts`, реквизит `lib/dungeon-props.ts`, крысы
`lib/dungeon-rats.ts`, генератор карт `scripts/dungeon-mapgen.py`.

- **Плитки — 0x72 DungeonTileset II v1.7, CC0** (0x72.itch.io/dungeontileset-ii).
  itch.io отсюда не открывается, атлас взят из копии в чужом репозитории на
  GitHub (`degtyarikup-ui/emberdeep`, папка `vendor/`). В проекте один атлас
  512×512 (40 КБ, `public/dungeon/x72/`) и координаты 370 кадров.
- **Репозиторий ПУБЛИЧНЫЙ — берём только CC0/CC-BY.** Отклонены: 32rogues
  (в лицензии прямо «You may not redistribute or resell it»), Pixel Crawler
  (нельзя перепродавать сами файлы, а условия лежат только в документе
  автора — выложить файлы в открытый репозиторий значит раздать их),
  «Free Rat Pack» Phewcumber (файлы не распространять). Поэтому **крысы
  нарисованы кодом**, а не взяты из набора: хорошего свободного набора крыс
  с нужными позами не нашлось.
- **Язык стен.** Над полом — лицо стены в одну клетку, сверху кромка: полоса
  в 5 точек с разделителями через 7 точек, посчитанными от МИРОВЫХ
  координат (иначе на стыке клеток шов). За кромкой тёмная порода без ярких
  крапинок: с ними пустота читалась звёздным небом.
- **Два вида пола, и лицо стены следует за полом ПОД ней**: над плитами —
  кирпич, над грунтом — дикая порода с крепью из двух стоек. Иначе в
  природной пещере Устья росла кирпичная кладка. `,` на карте — «другой»
  пол района: в Устье по умолчанию плиты, а `,` — грунт пещер; в Откатке
  наоборот (`floorLookOf`, `World.alt`). Предметы на клетке берут вид пола
  у большинства соседей.
- **Ключ кеша обязан покрывать картинку.** Вариант плиты выводится из
  ключа, а не из координат: иначе вид клетки зависел бы от того, какая
  клетка первой легла в кеш. Грунт и скальное лицо сшиты шумом с соседями —
  их не кешируем вовсе.
- **Кусок карты собирается в ОДНОМ буфере пикселей** (`blit` в `Px`) и
  выводится на холст одним вызовом; холстами поверх рисуется только старое
  (площадка клети, решётка, трещины, завал). Клетки плиток отдают `Px`, не
  холст. Раньше каждая клетка грунта и скального лица создавала свой
  холст — около 250 на кусок: 18,5 мс в среднем и до 70 мс на кусок, то
  есть запинка, когда кусок въезжал в экран. Стало 4,9 мс в среднем, p90 —
  9. Решётка шума с кешем почти ничего не дала: цена была в холстах.
  Кусков в памяти не больше 40 (вытесняется давно не нужный), и на кадр
  заранее рисуется один недостающий кусок из кольца вокруг экрана.
- **Мелочь на грунте** (`groundLitter`): кости, череп из атласа, щепа,
  самородок пирита, ржавый костыль — одна клетка из 40 и только на голом
  полу, не на рельсах и лужах. Кости — рисунком с шишками на концах: линией
  они читались закорючками.
- **Карты 64 в ширину**: Откатка 240 рядов, Устье 170 (было 40×219 на
  двоих). Правится только скриптом (`--write` переписывает
  `dungeon-maps.ts`, повторный запуск даёт тот же файл байт в байт). Ходок
  от решётки инструментальной Устья до зала клети Откатки обязан быть
  КОРОЧЕ главного пути (387 клеток против 425), иначе решётка ничего не
  даёт: ради этого главный путь нарочно изогнут.
- **Сохранение знает версию карты** (`MAP_VERSION`, сейчас 2). Сменилась
  планировка — разведка, фонари, решётки и тайники сбрасываются (номера и
  координаты больше ничего не значат), вылазка встаёт у клети, сидор
  остаётся. Сдвинули стены — поднимите версию, иначе герой очнётся в породе.
- **Баланс Откатки на новой карте** держат прежние тесты: Т2+0 без еды —
  3 смерти из 6, Т2+5 — ни одной; убийств 190–400 за 5 минут (на старой
  карте 223–310). Сначала норы и стаи добавил с запасом — вышло ноль
  смертей, пришлось срезать вдвое.
- **Крысы — параметрические**: два эллипса (бедро и грудь), голова с
  клином морды, тень по нормали со светом сверху-слева, хвост сплайном,

  фигуре, иначе в узле хвостов двоилась.

  вагонетка, стойка крепи, фонарь, табличка, норы, лампы, вход в шахту)
  нарисовано в палитре атласа: у 0x72 нет шахтёрского реквизита.
- **Стенд.** Режиссёр кормит крысами бесконечно, пока герой стоит у нор, —
  это задумано (норы заколачивают). Бот, который останавливается драться
  с каждой крысой в пяти клетках, так и простоит у первой норы все три

- **Не проверено на телефоне**: замеры кадра — со стенда (headless
  Chromium рисует софтверно). Если на живом телефоне дёргается при въезде

## Звук и музыка (v2.63.0) — `lib/sound.ts`, `public/audio`, `scripts/audio-build.py`

Владелец: «нужна колоссальная работа с музыкой и звуками для всего… а то у
нас из ушей кровь идёт». До этой версии каждый звук синтезировался
осциллятором (квадрат и пила на высоких частотах), а вращение барабана
было шумовым щелчком каждые 55–80 мс — 12–18 щелчков в секунду.

- **Всё — записи из свободных наборов, синтеза больше нет.** Эффекты —
  Kenney (CC0) и CC0-паки OpenGameArt через индекс
  `github.com/Mcamento8/open-game-sfx-index` (в нём проверено
  происхождение каждого пака); музыка — 9 треков CC0 (Tallbeard Studios /
  Abstraction «Music Loop Bundle» и yd) из `github.com/jfpx/cc0-media-library`,
  релиз music-v1, хеш архива сверен. Писк крыс — примеры мода Squeaky Ratkin:
  авторы объявили их общественным достоянием, но происхождение не
  гарантируют — это единственное пограничное место, записано в CREDITS.
  **Отсюда открываются только GitHub, npm и PyPI** — kenney.nl,
  opengameart, freesound, archive.org недоступны; поэтому источники —
  зеркала на GitHub. Не берите ничего без явной CC0/CC-BY.
- **Выбрано БЕЗ прослушивания** — по замерам: спектрограммы, пик, средняя
  громкость, спектральный центроид, для музыки — доля резкой середины
  2–6 кГц (`harsh`; брались треки до 0,13, drum-and-bass с 0,31 отброшен),
  для джинглов — контур основного тона (вверх — выигрыш, вниз — смерть).
  Если владельцу что-то режет ухо — меняйте сопоставление в
  `scripts/audio-build.py`, а не громкость в коде.
- **Сборка** (`scripts/audio-build.py`, нужны numpy и ffmpeg из
  `pip install imageio-ffmpeg`): обрезка тишины в начале (удар звучит в тот
  же кадр, что и картинка), хвост с затуханием, выравнивание к −18 дБ RMS
  с пиком не выше −1 дБ, моно MP3 96 кбит/с. Музыка — постоянный сдвиг к
  −19 LUFS без обрезки: длина в сэмплах сохраняется, иначе петля не
  сходится. Пути к исходникам — переменные `AUDIO_SFX`, `AUDIO_RAT`,
  `AUDIO_MUSIC` (шапка скрипта). Скрипт пишет `src/lib/audio-manifest.ts`
  (число вариантов, длины петель, ревизия `AUDIO_REV`) и
  `public/audio/SOURCES.txt`; `CREDITS.txt` ведётся руками.
- **MP3, а не OGG**: Safari (и iOS-вебвью Telegram) не декодирует Vorbis.
  Задержку кодера Chromium срезает сам (длина петли на стенде совпала до
  сотых миллисекунды); на случай, если браузер не срежет, `leadOf`
  пропускает тишину в начале сэмпла, а у музыки точки петли ставятся по
  настоящей длине трека из манифеста.
- **Движок** (`lib/sound.ts`): две шины (эффекты 0,9, музыка 0,42) → мягкий
  компрессор → выход. У каждого события несколько вариантов и разброс
  высоты ±4%, подряд один вариант не повторяется. `GAP` — минимальный
  промежуток между запусками, `VOICES` — сколько звучит разом: без них
  дождь монет и кирка на удержании складывались в перегруз. Имена
  экспортов прежние (57 функций) — вызовы по игре не менялись.
- **Вращение барабанов — одна петля** (`reelSpin`), а не щелчок по
  таймеру; `reelTick` оставлен тихим щелчком для колеса наград.
- **Джинглы по месту** (`voice()`): в зале, «Слотах» и «Каскаде» —
  стил-драм, в каторге (шахта, лес, двор, подземелье) — пиццикато, та же
  мелодия. Место берётся из последней музыкальной сцены. Под джингл
  музыка приглушается (`duck`).
- **Музыка по сценам**: зал, слоты, каскад, двор, шахта (в спецзоне —
  глубина), лес, лобби подземелья, глубина, король (ставит сама вылазка,
  пока у короля есть полоса здоровья). Страница зовёт
  `useGameAudio(сцена, наборы)`: настройки из стора, подгрузка своих
  эффектов, смена трека кроссфейдом; ушли из игр — тишина. Свернули
  Telegram — контекст на паузе. Музыка стартует с первого касания
  (слушатель `pointerdown` на окне) — раньше iOS не даст.
- **Настройка «Музыка»** (`slotsMusic`) отдельно от «Звука»: выключенный
  звук глушит всё, музыку можно выключить одну. Кнопки
  (`components/AudioToggles`) — в шапке зала, двора и подземелья, в шапке
  леса, в настройках шахты, в паузе вылазки; в «Слотах» и «Каскаде» —
  строкой в настройках.
- **Кеш**: service worker кладёт `/audio/` в `coco-audio` (CacheFirst,
  90 дней), в прекеш аудио не входит (9 МБ). В адресе `?v=AUDIO_REV` —
  пересобранный звук не отдастся из старого кеша.
- **Не проверено ухом и на телефоне.** Стенд подтверждает только, что файлы
  грузятся, декодируются и запускаются на нужных событиях.

## Живность шахты и риск-игра (v2.64.0) — `lib/critters.ts`, `components/Critters.tsx`

Первая часть плана по видео про Prison Evo (DiamondWorld). Взято только то,
что вписывается: поле, которое живёт само, и «рискнуть» — родная для
приложения механика. Кувалда (заряжаемый снос слоя) из плана выкинута:
в шахте уже девять способов снести кучу блоков.

- **Летучая мышь** вспархивает от ударов (`BAT_PER_BLOCK` 1/550, не чаще
  раза в 100 с — примерно раз в четыре минуты копания), не летает, пока
  ждёт сундучок и пока на поле метеорит, Куйва или сорока. **Ловится только
  тапом по ней** — это и есть вся игра с ней; ведение пальцем её не берёт.
  Зона нажатия — 1,7 клетки: цель движется. Синяя (12%) быстрее, светится
  и платит в 2,5 раза больше.
- **Сундучок «одна из трёх»**: три РАЗНЫХ рода (монеты, токены, ключ,
  расходник, руна), среди них всегда монеты или токены — то, чем можно
  рискнуть. Цены карт примерно равны (ключ ≈ сундук ≈ 4% цены ранга ≈
  токены по рангу), чтобы выбор зависел от нужды, а не от арифметики.
- **Мышь проходит тест темпа** и стоит ≈4% круга A→Z (1,53 → 1,47 ч,
  худшее зерно 1,42). С первой прикидкой (5% цены и 10+3·ранг токенов,
  раз в 50 с) она съедала 7% — внимание превращалось в доход. Щедрее не
  делайте: граница 1,4 ч упадёт. Токены весят больше монет: они идут в
  чары, а чары — главная кривая силы.
- **Сорока-воровка** — событие двора (24 с): летает, отскакивая от краёв,
  роняет блестяшки в клетку под собой; лежат 3,2 с и мигают перед концом.
  **Подбираются любым ударом по клетке** (`specialHit` спрашивает
  `takeAt` раньше породы): тап, удержание, ведение — в этом суть налёта.
  Монеты копятся в мешочке (`event.have`, видно на плашке события), токены
  и ключ (не больше одного за налёт, счёт в `event.need`) — сразу. Улетела
  — мешочек становится сундучком, им можно рискнуть.
- **Сундучок один** (`prison.treasure`, переживает перезапуск). Если он уже
  ждёт решения, когда сорока улетает, мешочек платится сразу: второй
  затёр бы первый.
- **Риск — «удвойка» старых автоматов**: открыта карта сдающего, четыре
  рубашкой вверх, старше — вдвое, младше — сгорело, равная — ещё раз.
  **Карта сдающего открывается ДО выбора, и отказаться после неё нельзя**
  (`prisonRiskDeal` пишет сразу, со сбросом всех записей на диск) — иначе
  рисковали бы только на двойке, и удвойка стала бы бесплатными деньгами.
  В среднем честная: тест держит P(выиграл) = P(проиграл) и среднюю ставку
  ≈1. Не больше четырёх удвоений (×16). Рискуют только монеты и токены.
- **Двигается rAF, а не React**: мышь и сорока пишут `transform` прямо в
  элемент, центровка — свойством `translate`, поэтому анимация удара
  (WAAPI по `transform`) её не сбивает. Карты переворачиваются 3D-поворотом
  с двумя гранями (`backface-visibility`), остальные три — с задержкой.
- **Картинки**: колода — Kenney «Playing Cards Pack» (CC0), рубашка
  перекрашена в цвета лагеря; мыши — Pixel-boy (CC0, из Superpowers Asset
  Packs); сорока нарисована по пикселям. Всё собирает
  `scripts/critters-assets.py` (пути к клонам — `KENNEY`, `SUPERPOWERS`).
  Первая сорока читалась уткой: толстое тело, короткий хвост. Сороку
  делают длинный хвост (почти в длину тела), белое плечо и синее крыло.
- **Стенд**: в разработке `window.__mine.bat(true)` выпускает мышь руками.
  Vite-сервер останавливайте по номеру процесса из `/proc`, а не
  `pkill -f` — тот убивает собственную оболочку (наступил снова).
- Достижение «Ловец мышей» — тридцать пойманных (`prison.bats`).

  дольше ждать, но чаще редкие), ПОДСЕЧКА (холостые подёргивания, потом
  поплавок уходит под воду — тап в окно `hookWindow`; тапнул раньше —
  спугнул) и ВЫВАЖИВАНИЕ (`stepFight`: держишь — катушка тянет, натяжение
  растёт; рывок рыбы гонит его в красное — отпускай; провисла на 2 с —
  ушла; в красном 0,5 с — леска лопнула).
- **Бой настроен ботом с реакцией 0,2 с**, а не на глаз: рыба слабее
  удочки ловится почти всегда, вдвое сильнее — 65–97%, втрое — меньше 10%.
  Первая версия без задержки реакции прощала всё и тянулась по 30–50 с,
  вторая обрывалась стеной. Сила рывков случайная (`burstK`): слабый можно
  пересидеть, сильный — только отпустить, отсюда плавный рост риска.
- **Удочка N — под место N** (`rodReach`, тест): обычная и редкая рыба места
  среднего веса не сильнее удочки в 1,6 раза. Эпическую и легенду это не
  обещает — их тянут руками. Золотая — под сома, тайменя, тунца и осетра.
  Первая формулировка считала только обычную рыбу, и Самоделка с Бамбуковой
  обе писали «до Реки» — подсказка ничего не различала.
- **Клёв у каждого места свой** (`bite`, `biteAt`): каждая вытащенная штука
  проедает 6%, отрастает 12% в минуту, дно 15%. Слабый клёв — дольше ждать
  и мельче рыба. Это то, что гонит по местам, а не заставляет стоять на
  одном.
- **Доход в минуту держит тест**: пруд ≈500 (как ива в лесу), каждое место
  больше чем вдвое прошлого, море ≈24 тыс. — МЕНЬШЕ верхней делянки леса
  (≈33 тыс.). Рыба — ещё один промысел, а не станок мимо шахты. Первая
  прикидка дала морю 33,6 тыс. — базы мест срезаны.
- **Общее с каторгой, и каждое к делу**: кошелёк (садок продаётся с той же
  надбавкой `modsOf().sell`, что порода и лес), токены (первая рыба вида),
  питомец (кнопка «Кормить» отдаёт ему садок вместо денег — 22 опыта за
  рыбу, настоящий выбор), сундучок «одна из трёх» (шкатулка со дна, 2,5%;
  сундучок занят — токенами) и **жемчуг**: 14% ракушек, +0,5% к продаже
  ВЕЗДЕ, не больше десяти. Живёт в `prison.pearls`, потому что его читает
  `modsOf`, а prison.ts рыбалку не знает. Руны рыбалке ничего не дают —
  поэтому вкладки рун в лагере рыбака нет.
- **Своё сохранение** (`fishing.state`), как у леса; сбросы из настроек
  обнуляют и его.
- **Страница пишет кадр мимо React**: поплавок, леску, удилище и полосы
  двигает rAF-цикл прямо в DOM, состояние меняется только на границах фаз.
- **Грабля**: эффекты размера сцены и канвы брызг ждали только `hydrated`.
  Если рыбалка открывалась, пока страница уже стояла закрытой (ранг ниже D),
  сцена так и не мерилась — удочка и поплавок не рисовались вовсе. Теперь
  они ждут `sceneOn`.
- **Сундучок на рыбалке — только в покое** (`phase === 'idle'`): поверх
  карточки улова и боя он перекрывал бы руки.
- **Сцена — статичная SVG-картинка по месту**: солнце или луна, дорожка на
  воде, облака, звёзды у моря, снег на пиках горного озера (тот же силуэт
  под `clipPath`), камыш и кувшинки. Движутся только два слоя бликов
  (transform). Высота сцены — `100dvh − 318 px`, замерено на стенде.
- **Рыбы нарисованы кодом** (`scripts/fish-assets.py`): лист 40×16 на
  клетку, по 8 в ряд, порядок как в `FISH`; 26 — ракушка, 27 — жемчужина,
  28 — поплавок. Хвосты длинных рыб резались — клетка стала 40 в ширину, а
  рыба центрируется. Иконки удочки, рыб и садка — game-icons (Delapouite).
- **Звуки** — всплеск, «плюх» поплавка, щелчок катушки, лопнувшая леска;
  музыка сцены — «Ambient Relaxing Loop» из того же CC0-набора.
- **Стенд**: в разработке `window.__fish.bite()` вызывает поклёвку сразу.
  Бот стенда (тянет, пока натяжение ниже 0,85, отпускает выше) вытаскивает
  треску на Телескопе за 10–14 с. **Не проверено ухом и на телефоне.**

## Скины: как их получают

- **Обычные открывает уровень** (`SKIN_UNLOCK`), то есть время за игрой.
- **«Реликвия» (`relic`) — единственный скин-достижение.** Её условие —
  `topX >= 200`, то есть выигрыш от 200 ставок за один спин (ступень
  «МЕГА-ВЫИГРЫШ» из `lib/rollup.ts` — не случайное число, а та же лестница,
  по которой игра называет выигрыши). Уровень её не открывает НИКОГДА, и это
  принципиально: уровень набивается усидчивостью, а такой спин нужно взять.
  Опустите порог — и скин перестанет что-либо значить.
- **`topX` меряется в СТАВКАХ, а не в монетах.** «Лучший спин» в монетах
  зависит от ставки и не говорит ни о чём: тысяча монет при ставке 1000 —
  это возврат, а при ставке 10 — событие. Пишется в обеих играх; в «Слотах»
  считается от ИТОГА, чтобы сорванный джекпот тоже шёл в зачёт.
- **Условие без прогресса — это не цель, а отказ.** На карточке всегда видно
  «ваш лучший — ×83 из ×200», и запертая «Реликвия» не гаснет до серого: её
  должно быть видно, иначе за ней не пойдут.
- **Владельцу заработанные скины ВЫДАНЫ** — без условия, флагом с сервера.
  Владелец попросил скин себе («эти 200x я не могу выбить»), и здесь была
  развилка: опустить порог или выдать. Опустить — значит обесценить скин
  навсегда и для всех; выдать — это ровно один аккаунт, и он же этот скин и
  заказывал. Поэтому `RELIC_X` не тронут, а `isSkinAvailable` получил
  четвёртый аргумент `granted`. Флаг берётся из `/api/backup/status` — того
  же ответа, по которому показывается диагностика «Кассы»: сервер сверяет id
  из подписанного Telegram `initData` с настроенным админом, так что из
  приложения его не подделать. Карточка при этом НЕ врёт: пока `topX` ниже
  порога, на ней «ВЫДАНО» и «выдан владельцу автомата», а не «добыт спином» —
  иначе она приписывала бы игроку чужой рекорд.
- **Ответ сервера про владельца — трёхзначный: да, нет и «ещё не знаем».**
  Пока `owner === null`, страховка «сброситься на Классику, если скин стал
  недоступен» обязана молчать: иначе она на первом же кадре вышибет
  владельца с выданного скина, потому что ответ ещё в пути. И отказ сети не
  отменяет прошлое «да» — скин, пропадающий при моргнувшем интернете, хуже
  скина, выданного на слово сервера минуту назад.
- **Своя анимация есть ТОЛЬКО у «Реликвии»** — этим она и отличается, а не
  другим набором картинок. Три слоя на весь экран: ореол корпуса
  (конический градиент, нарисован один раз и крутится трансформом), блик по
  вывеске (проходит раз в пять секунд — редкий проход важнее яркого) и
  золотая пыль в сцене (тот же приём, что снег в «Зиме»). Больше слоёв — это
  уже не роскошь, а тормоза; правила бюджета кадра те же, что выше.
- **У «Реликвии» ТЁМНЫЕ барабаны.** На кремовой ленте, как у всех остальных,
  золото символов сливается с золотом корпуса и поле читается стеной
  одинаковых монет. Тёмная лента с тех пор появилась ещё у «Купальской ночи»
  (см. ниже) — и там она обязательна по той же причине, только с другой
  стороны: символы светятся сами.
- Раньше тут был механизм сезонных окон (`skin-limits.ts`): скины выдавались
  на время и оставались навсегда, если успел взять. Владелец попросил снять
  лимит («хочу, чтобы они всегда были»), и механизм удалён вместе с тестами —
  не восстанавливайте его без запроса. Сам приём рабочий, если сезонность
  когда-нибудь понадобится снова.
### «Купальская ночь» (`kupala`) — флагман

Единственный скин, который переделан ЦЕЛИКОМ: символы, палитра, корпус,
вывеска, безель, лента, решётка клеток, подсветка выигрыша, табло, строка
статуса, все кнопки, поддон, рычаг и фон сцены. Остальные скины — это
палитра плюс декор; здесь заменён каждый пункт списка.

- **Символы нарисованы, а не взяты из Twemoji.** `public/slots/kupala/*.svg` —
  свои, `viewBox 0 0 64 64`, без фильтров и CSS-переменных, ~21 КБ на все
  восемь (Twemoji-скин весит 36–40). Лестница со смыслом: внизу лист
  папоротника, наверху цвет папоротника — тот самый клад из легенды.
  Цвет разведён по кругу (зелёный, кармин, фиолет, синий, янтарь, белый,
  лайм, оранжевый), силуэты — по классам формы. Проверено на случайном
  поле 6×5, а не на ряду из восьми иконок.
- **Материал — палехская лаковая шкатулка,** а не «ещё одна палитра». Три
  материала: корпус чёрный лак, фурнитура латунь (`--bezel-*`), вставки
  перламутр (`--nacre`). Производные `--nacre`, `--brass`, `--spec` живут в
  палитре скина и больше нигде. **Лак не светится сам, он ОТРАЖАЕТ** —
  поэтому цвет приходит на корпус СНИЗУ, от пола сцены, в отличие от всех
  остальных скинов. Уберёте жёсткий узкий блик (`--spec`) или размажете его
  стопы — материал пропадёт и скин прочитается как «тёмная Классика».
- **Закон движения: МЕТАЛЛ ЩЁЛКАЕТ, СВЕТ ТЕЧЁТ.** Железное (лампы, блик по
  латунной табличке, нажатие клавиш) перещёлкивает через `steps()` и стоит
  один композиторский такт за щелчок; светящееся (перламутровая инкрустация,
  светляки в сцене) движется плавно. Это единственное деление, и оно держит
  весь скин. Сделаете блик по вывеске плавным — получите «Реликвию»;
  сделаете светляки ступенчатыми — получите сломанный телевизор.
- **Постоянно анимируемых слоёв ровно три:** инкрустация корпуса (`opacity`),
  блик по вывеске (`transform`, 8 остановок) и светляки (`transform`).
  Базовые `neon-flicker` на вывеске и пульс `is-busy` на главной кнопке
  выключены намеренно — чистый прирост к базовому скину +1 слой.
- **Вращать внутри `.cabinet` нельзя.** У него скруглённый `overflow: hidden`,
  и вращающийся потомок под таким клипом на части Android WebView снимается
  с композитора. Инкрустация поэтому только мигает прозрачностью; всё
  вращающееся живёт в сцене, где клипа нет. По той же причине **внешний
  ореол только `box-shadow` на самом корпусе** — псевдоэлемент обрежется.
- **Решётка клеток нарисована на КОЛОНКЕ, а не на клетках.** Один статичный
  `repeating-linear-gradient` с шагом `var(--cell)` / `var(--scell)`, ноль
  новых элементов на тридцать клеток. Она принадлежит окну, поэтому при
  вращении стоит на месте — и вращение читается как движение за решёткой.
  Слои ленты и решётки обязаны быть в ОДНОМ `background`: отдельное
  `background-image` молча затрёт список.
- **Текст берёт `--ink`, а не `--reel-hi`.** Скины со светлой лентой красят
  строку статуса и надписи кнопок через `--reel-hi`; здесь лента тёмная, и
  это дало бы тёмное по тёмному. `--ink` заведён ровно для этого.
- **Что в скине выключено намеренно:** `backdrop-filter`, `mix-blend-mode`,
  анимации `filter`/`blur()`, `background-position` и `box-shadow`,
  вращающиеся слои внутри скруглённого `overflow: hidden`.
- Скин переопределяет у себя лампы, тени ленты и подсветку выигрыша. Те же
  места позже починены и в базе, для всех скинов сразу — см. ниже.

### Что в базе было захардкожено мимо палитры (починено)

Четыре места жили с прибитыми цветами, и ни один скин их не менял, поэтому
«Космос», «Зима» и «Из глубины» носили тёплые оранжевые детали на холодном
корпусе. Все четыре теперь считаются из токенов:

- **Лампы корпуса** — были `#ffd9a3` и свечение `#ffb459`. Светлое ядро
  оставлено намеренно: лампа обязана быть светлее своего свечения, иначе она
  читается пятном краски, а не источником.
- **Inset-тени ленты** — были коричневые (`rgba(90,50,20,…)`), от чего
  холодная лента выглядела грязной. Стали чистой чернотой: она нейтральна к
  любой палитре и даёт ту же глубину.
- **Подсветка выигрыша** (`.reels__mark`, `.sbcell.is-win::before`) — было
  золото `#ffb43c` / `#ffc23c`. Формула теперь ДВУХКАНТОВАЯ: тёмная
  волосяная линия → насыщенный тёмный кант оттенка скина → светлая нить. Так
  рамка читается и на кремовой ленте (её держит тёмный кант), и на тёмной
  («Реликвия», «Купальская ночь» — их держит светлая нить). Одним светлым
  кантом обойтись нельзя: пробовал, и на «Классике» рамка почти пропала —
  светлое по светлому.
- **`--speed` в «Слотах»** — переменная задавалась только в `ScatterPage`, и
  `var(--speed,1)` в «Слотах» всегда был 1: турбо сжимал таймеры, а жетон,
  титул ступени и счётчик шли в полную длину и обрывались следующим звеном.
  Значение обязано совпадать с долей таймеров той же страницы (0.55), иначе
  CSS и JS разъедутся.

- Новый скин = каталог `public/slots/<id>/` на 8 файлов (7 символов +
  `scatter`, из Twemoji), запись в `SKINS`, палитра и декор в `theme.css`.
  **Проверяйте набор глазами на одном листе**: дважды ловил то три белёсых
  символа подряд, то два фиолетовых — по отдельности всё хорошо, а на поле
  каша.

## Conventions

- Commit messages in this repo are short and in Russian (e.g. `feat(calc): …`).
- Do not commit secrets. `dist/` and `node_modules/` are build artifacts (git-ignored).
- The app runs inside Telegram's webview (mobile-first); the calculator pins itself to
  the viewport and uses pointer gestures — test touch behaviour, not just desktop.
- **Bump the version on every deploy.** `src/version.ts` holds `APP_VERSION` — raise it
  for each user-visible release and name it in the commit. It's shown in the home
  screen's bottom corner (with the Vite-injected build time) so the user can confirm a
  fresh build actually loaded (vs. a stale PWA cache).
